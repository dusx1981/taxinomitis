# Session-users 班级 vs. 其他班级认证逻辑详细说明

---

## 1. Session-users 班级的本地 JWT 验证流程

**适用场景**：  
当请求访问路径中包含 `classid = sessionusers.CLASS_NAME`（特殊班级）时触发

```js
if ((req.params.classid === sessionusers.CLASS_NAME) &&
    req.headers.authorization?.startsWith('Bearer')) {
    const jwtToken = req.headers.authorization.split(' ')[1];
    sessionusersAuthenticate(jwtToken, req, res, next);
}
````

### 分步验证流程

1. **JWT 解码**

```js
try {
    decoded = jwtDecode(jwtTokenString); // 无签名验证的简单解码
} catch (err) {
    return errors.notAuthorised(res); // 401
}
```

* 仅解析 JWT 结构，不验证签名
* 无效结构 → 立即返回 401

2. **令牌有效性验证**

```js
const sessionUserIsAuthenticated = await sessionusers.checkSessionToken(
    req.params.studentid, // 路径中的学生ID
    decoded.token         // JWT 中的令牌字段
);
```

* 核心验证方法：`sessionusers.checkSessionToken()`
* 验证逻辑：

  * 检查令牌是否存在于本地存储
  * 验证令牌是否过期
  * 确认令牌关联的学生ID与路径参数匹配

3. **构建用户对象**

```js
reqWithUser.user = {
    sub: decoded.id, // 使用解码后的用户ID
    app_metadata: {
        role: 'student',
        tenant: sessionusers.CLASS_NAME // 固定为特殊班级名
    },
    session: decoded // 存储完整解码对象
};
```

* 固定角色为 `student`
* 固定租户为 `sessionusers.CLASS_NAME`
* 存储原始解码数据供后续使用

4. **流程控制**

* 验证成功 → 调用 `next()` 进入后续中间件
* 验证失败 → 返回 401 未授权

### 安全特性

* ⚠️ **无签名验证**：依赖本地存储校验而非密码学验证
* 🔒 **最小权限**：强制设置固定角色和租户
* 📍 **上下文绑定**：令牌必须与请求路径的学生ID匹配

## 2. 其他班级的 Auth0 OAuth 2.0 验证流程

**适用场景**：
所有非 `session-users` 班级的请求

```js
const auth0Authenticate = expressjwt({
    secret: jwksRsa.expressJwtSecret({
        cache: true,
        jwksUri: `https://${authvalues.DOMAIN}/.well-known/jwks.json`
    }),
    aud: authvalues.AUDIENCE,
    issuer: `https://${authvalues.CUSTOM_DOMAIN}/`,
    algorithms: ['RS256'],
    requestProperty: 'user'
});
```

### 分步验证流程

1. **JWKS 公钥获取**

```js
jwksRsa.expressJwtSecret({
    jwksUri: 'https://AUTH0_DOMAIN/.well-known/jwks.json'
})
```

* 动态获取 Auth0 JWKS 端点公钥
* 自动缓存和刷新公钥
* 内置速率限制（5请求/分钟）

2. **JWT 签名验证**

* `algorithms: ['RS256']` → 强制使用 RS256 非对称加密
* 使用 JWKS 公钥验证 RS256 签名
* 防止令牌篡改（签名无效立即拒绝）

3. **声明验证**

```js
aud: authvalues.AUDIENCE
issuer: `https://${authvalues.CUSTOM_DOMAIN}/`
```

* 验证 `aud` (受众)：必须匹配注册的客户端ID
* 验证 `iss` (签发者)：必须匹配 Auth0 域名
* 验证令牌有效期（自动检查 `exp` 声明）

4. **用户对象注入**

* `requestProperty: 'user'` → 注入到 `req.user`
* 成功验证后，将 JWT payload 注入到 `req.user`
* 包含标准声明：`sub`, `iat`, `exp` 等
* 包含自定义声明（如角色和租户信息）

### 验证失败处理

* 签名无效 → 401 Unauthorized
* 受众不匹配 → 401 Unauthorized
* 签发者不匹配 → 401 Unauthorized
* 令牌过期 → 401 Unauthorized

## 核心差异对比

| 特性   | Session-users 本地验证 | Auth0 OAuth 2.0 验证                 |
| ---- | ------------------ | ---------------------------------- |
| 验证方式 | 本地数据库查询            | 密码学签名验证                            |
| 签名检查 | ❌ 无                | ✅ RS256 非对称加密                      |
| 令牌类型 | 简单 JWT（无敏感数据）      | 标准 OAuth 2.0 访问令牌                  |
| 角色管理 | 固定为 student        | 动态声明（student/supervisor/siteadmin） |
| 租户管理 | 固定为特殊班级            | 动态声明（多租户支持）                        |
| 错误处理 | 统一返回 401           | 详细错误分类                             |
| 依赖服务 | 本地数据库              | Auth0 服务 + JWKS 端点                 |
| 性能影响 | 数据库查询开销            | 公钥缓存减少计算开销                         |
| 适用场景 | 临时会话用户             | 正式注册用户                             |

---

## 为什么采用混合模式？

1. **特殊场景优化**

   * Session-users 用于临时/匿名用户，避免 Auth0 计费开销
   * 简化临时用户的认证流程

2. **安全分级**

   * 正式用户：企业级安全（Auth0）
   * 临时用户：轻量级安全（本地验证）

3. **成本效益**

   * 减少 Auth0 认证调用次数
   * 本地验证降低外部依赖

4. **架构灵活性**

   * 特殊班级可独立扩展
   * 不影响主系统认证流程

> 这种混合模式在保证核心系统安全性的同时，为特定场景提供了高效轻量级认证方案。
