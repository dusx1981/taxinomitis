# Session-users 班级 vs. 其他班级认证示例说明

---

## 场景 1：临时学生访问项目（Session-users 班级）

**用户背景**：  
小明是临时访问的学生，未注册正式账号，通过一次性链接进入系统。

**请求示例**:
```http
POST /classes/session-users/students/temp-12345/projects
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpZCI6InRlbXAtMTIzNDUiLCJ0b2tlbiI6IjEyMzQ1Njc4OTAiLCJpYXQiOjE2OTUyMzQ1NjB9.xxxx
````

**认证流程**：

1. **路径识别**

   * `classid=session-users` → 触发本地认证流程

2. **JWT 解码**

```json
{
  "id": "temp-12345",
  "token": "1234567890",
  "iat": 1695234560
}
```

3. **本地验证**

```js
await sessionusers.checkSessionToken(
  "temp-12345",       // 路径中的学生ID
  "1234567890"        // JWT 中的 token 字段
);
```

* 验证逻辑：

  * ✅ 检查 `temp-12345` 用户是否存在
  * ✅ 检查令牌 `1234567890` 是否有效且未过期
  * ✅ 确认令牌属于用户 `temp-12345`

4. **构建用户对象**

```js
req.user = {
  sub: "temp-12345",
  app_metadata: {
    role: "student",          // 固定角色
    tenant: "session-users"   // 固定租户
  },
  session: {                  // 存储原始数据
    id: "temp-12345",
    token: "1234567890",
    iat: 1695234560
  }
}
```

5. **访问控制**

* 仅能访问 `/session-users/` 路径下的资源
* 角色固定为 `student`，无升级权限

## 场景 2：注册学生访问项目（其他班级）

**用户背景**：
小红是注册学生，属于 `"science-class-10a"` 班级，通过学校账号登录。

**请求示例**:

```http
POST /classes/science-class-10a/students/auth0|6172b1b31d9f8e0069f4c3f0/projects
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.xxxx
```

**认证流程**：

1. **路径识别**

   * `classid=science-class-10a` → 触发 Auth0 认证

2. **JWT 验证**

```js
secret: jwksRsa.expressJwtSecret({
  jwksUri: "https://mlforkids.auth0.com/.well-known/jwks.json"
}),
aud: "mlk-app-clientid",
issuer: "https://mlforkids.auth0.com/"
```

* 验证步骤：

  * ✅ 从 JWKS 端点获取公钥
  * ✅ 用 RS256 算法验证签名
  * ✅ 检查受众是否为 `mlk-app-clientid`
  * ✅ 检查签发者为 `https://mlforkids.auth0.com/`

3. **解析声明**

```json
{
  "sub": "auth0|6172b1b31d9f8e0069f4c3f0",
  "https://mlforkids.co.uk/api/role": "student",
  "https://mlforkids.co.uk/api/tenant": "science-class-10a",
  "iat": 1695234560,
  "exp": 1695238160
}
```

4. **标准化用户对象**

```js
req.user = {
  sub: "auth0|6172b1b31d9f8e0069f4c3f0",
  app_metadata: { // 转换自定义声明
    role: "student",
    tenant: "science-class-10a"
  }
}
```

5. **租户验证**

```js
if (req.params.classid !== "science-class-10a") {
  return errors.forbidden(res); // 403
}
```

## 核心区别对比

| 特征    | Session-users 班级    | 其他班级             |                           |
| ----- | ------------------- | ---------------- | ------------------------- |
| 用户类型  | 临时/匿名用户             | 注册用户             |                           |
| 认证方式  | 本地数据库查询             | Auth0 OAuth 2.0  |                           |
| 令牌验证  | 简单令牌匹配              | RS256 密码学签名      |                           |
| 用户ID  | 简单ID (如 temp-12345) | 标准sub声明 (如 auth0 | 6172b1b31d9f8e0069f4c3f0) |
| 角色来源  | 固定为 student         | 从JWT声明动态获取       |                           |
| 租户来源  | 固定为 session-users   | 从JWT声明动态获取       |                           |
| 令牌有效期 | 本地控制 (通常较长)         | 标准 exp 声明 (通常较短) |                           |
| 权限范围  | 仅限 session-users 资源 | 多租户支持            |                           |
| 错误代码  | 统一 401 未授权          | 详细 401/403 错误    |                           |
| 典型场景  | 课堂临时演示 / 快速体验功能     | 正式课堂学习 / 长期项目开发  |                           |

---

## 为什么需要两种模式？

1. **教育场景需求**

   * 教师需要快速创建临时账号供学生课堂实践
   * 正式课程需要长期账号保存学习进度

2. **用户体验优化**

   * 临时用户免去注册流程
   * 注册用户获得完整功能

3. **成本控制**

   * Auth0 按认证次数计费
   * 临时用户使用本地验证降低成本

4. **安全平衡**

   * 临时会话：轻量级安全（低风险场景）
   * 正式账户：企业级安全（保护长期数据）

> 这种混合模式完美解决了教育场景中「快速体验」和「深入学习」的双重需求，在安全性和用户体验间取得平衡。
